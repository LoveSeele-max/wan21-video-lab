## 第 6-7 周：本人代码改动 + 16G 可用性

**性能型代码改动（至少 1 处）**：目标是降低延迟或峰值显存，选题由前几周的观测决定。候选：

- [ ] VAE 解码显存。上游时间维**已经逐帧解码**，不要重做。先用分阶段峰值，加上 `torch.cuda.memory._record_memory_history` 一类工具，定位峰值来源：
  - 单帧全分辨率激活 → 考虑**空间分块**（注意接缝）；
  - 输出逐帧 `torch.cat` 累积 → 考虑预分配，或逐帧移到 CPU；
  - 特征缓存 → 对照 `--vae_cache_cpu` 的现有效果。

  改完后逐帧比对，确认输出一致或误差可控。
- [ ] 其他由 profiler 发现的瓶颈

每处改动要求：**可解释**（为什么改）、**可测量**（前后对照）、**可回退**（默认行为不变或有开关）。

**非性能型改动**也值得做，可作为 PR 候选，但不计入上面的要求：
- [ ] 阶段计时 / 性能日志整理成可选开关
- [ ] `--fp8_fast` 未配 `--fp8_scaled` 时给出警告，以及其他文档与代码不一致处的修正

**16G 可用性（组 C，固定配置基线已在 Week 2 完成；候选配置对照仍待执行）**：

- [x] 本机 torch attention、BF16 固定配置完成 L0–L2 九次生成及性能测量，未记录 OOM；L3 在用户设置“偏好无系统内存回退”后仍成功。不据此宣称全程独立显存驻留。

- [ ] 服务器上：`--blocks_to_swap` 扫描若干档位，画出显存—延迟曲线（上限按第 1 周确认的层数）
- [ ] 服务器上：`--vae_cache_cpu` 与 fp8 组合的显存。**这张表只用于筛选本机候选**
- [ ] **本机 5060 Ti 16G**，按以下顺序：
  1. 先确定能跑通的 attention 后端（从 `torch` 开始）；
  2. 固定这个后端；
  3. 逐步加 fp8 / `--fp8_t5` / `--blocks_to_swap` / `--vae_cache_cpu`，直到能跑通；
  4. 跑通后再试 1~2 个候选配置，形成比较。
- [ ] **分两张表报告**：服务器表（权衡）、本机表（可运行配置的耗时与质量）
- [ ] 措辞：只跑通一个配置就写"找到可运行配置"；比较过多个配置，才写"已测配置中代价最小"

## 贯穿全程的三件事

1. **配置即文件**：每个实验配置写成 `configs/` 下的文件，结果表直接引用文件名，不靠记忆复述参数。
2. **每周记一笔日志**：`logs/weekN.md` 写本周跑了什么、数字是多少、遇到什么坑。这份日志最终直接变成报告素材。
3. **简历随时可投**：第 8 周之后每个阶段结束都可以再投一轮。不要攒到最后一次性投。

## 双卡怎么用

- **卡 0**：主线（当前阶段的实验）
- **卡 1**：无状态耦合的并行任务，如另一组候选项、基线生成、计时重复
- **本机 16G**：组 C 的实机验证平台，固定配置基线已完成，后续候选对照待执行；代码阅读、指标计算、小规模冒烟

**不要**把两张卡当一张 96G 用。**不要**在基础设置稳定前并行铺开训练对照。

## 削减优先级

预算不够时按此顺序砍：

1. 各扫描的取值**个数**（如步数从 8 档砍到 5 档）
2. 第 9-10 周的候选池补充
3. 次要线

**永远不砍**：冻结的验证提示词集、人工盲评、探针样本、瓶颈定位、至少一处本人性能型代码改动。
