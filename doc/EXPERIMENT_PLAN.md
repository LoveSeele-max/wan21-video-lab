## 一、为什么换题

旧主线研究"训练时间步分布是否影响动作适配"。在单训练种子、小提示词集、严格覆盖率纪律的条件下，**较可能的产出是"未检出显著差异"**。这样的结论很难单独撑起一个实习简历项目。

新主线是"定位视频 DiT 推理的瓶颈，并针对性优化"。它**更容易形成连续、可展示的交付**：每一步都有基线、测量和对照可写。不过数字本身不等于价值，项目价值仍取决于三点：问题是否选对、改动是否站得住、解释是否清楚。

### 保留与降级

| 原内容 | 处置 |
|---|---|
| 时间步采样、flow shift、min/max timestep、preserve_distribution_shape | **保留，降级为次要线**，并入阶段 4 |
| 采样步数质量—延时曲线（原阶段 5） | 并入阶段 2 候选池 |
| 单人物动作 LoRA | 保留，作为阶段 3 |
| 双层报告、生成种子与训练种子区分 | 保留**简化版**：覆盖率短表，见 METRICS.md 第四节 |
| MMD 分布距离、光流 warp 误差、ImageReward、多训练种子复核 | **推迟**，仅在次要线出现正效应后考虑 |
| 反例探针（正常/静止/闪烁/画质对但动作不符） | 保留，性价比最高的一块 |

## 二、研究问题

**主线**

> 固定 480P、帧数和提示词集，分三步回答：
> 1. Wan2.1 1.3B 一次生成的时间和显存**花在哪里**？
> 2. 针对其中最大的瓶颈，哪些现有选项或代码改动能把延迟或峰值显存降下来？各自的**质量代价与失效条件**是什么？
> 3. 暂缓：在 16G 消费卡上要跑起来，代价是多少？恢复本机实测后再回答。

**次要线**

> 时间步采样策略（`--timestep_sampling`、`--discrete_flow_shift`、`--min_timestep/--max_timestep`）和 LoRA 配置，如何影响模型学到的是"动作"，还是仅仅"外观"？

## 三、阶段划分

### 阶段 0：环境与复现

**目标**：在服务器上跑通官方推理，产出第一段视频。

- 固定 commit hash、依赖版本、权重版本，并记录下来（写入 `REPRO.md`）。
- 跑通 `wan_generate_video.py`。
- **参数核对以所选 commit 的源码和 `--help` 为准**，docs/wan.md 只作参考：已发现文档与代码不一致之处，见第七节。
- 用本项目实际用到的参数逐条核对 ASSUMPTIONS 第一、二节，把状态更新为"已核实（commit xxx）"。
- 选卡：`--device cuda:N` 或 `CUDA_VISIBLE_DEVICES` 都可以。双卡并行时推荐后者，隔离更彻底。

**交付**：一段 480P 视频 + 可复现的命令 + 环境记录 + 参数核对记录。

**止损线**：环境问题超过 3 天，就改用官方 Wan2.1 仓库的推理入口，不在包装脚本上卡着。

### 阶段 1：测量基线与瓶颈定位

**目标**：先把"怎么测"定死，再把"时间花在哪"测出来。**这一阶段不做优化。**

- 写测量脚本，操作定义见 METRICS.md 第一节：同步计时、预热后重置峰值统计、三种耗时分开定义。
- **分阶段计时**：
  - 模型加载
  - T5 文本编码
  - 去噪循环：总计和单步
  - VAE 解码
  - 保存

  上游生成脚本**没有任何阶段计时**（已核对源码），需要自己插桩。
- **跑一次 `torch.profiler`**，看去噪单步内 attention、线性层和其他算子的占比。
- 冻结一组提示词（10~20 条）和生成种子（3 个），写入配置。
- 跑通四个反例探针样本，确认人工判据可用（见 METRICS.md 第三节）。

**交付**：
- 测量脚本
- 基线数字表
- **阶段耗时分解表**
- **瓶颈结论**：一段话，说明时间与显存主要花在哪、证据是什么
- 冻结的提示词/种子清单

**止损线**：测量脚本不追求通用性，不写成通用 benchmark 框架。

### 阶段 2：推理优化（瓶颈驱动）

**原则**：**由阶段 1 的瓶颈结论决定做什么**，而不是把所有开关扫一遍。下表是**候选池，不是必做清单**。

**首版必做（第 8 周出口）**：

1. 性能基线（阶段 1 已完成）；
2. 瓶颈定位（阶段 1 已完成）；
3. **两组针对瓶颈的对照**：从候选池中选；
4. **至少一处本人的性能型代码改动**：目标是降低延迟或峰值显存，选题由观测决定，并且可解释、可测量、可回退。不预设上游一定有 bug。**阶段计时插桩是测量工具，不计入这一项。**

**候选池**（参数均已对照源码核实，2026-10-11，main 分支；执行时以所选 commit 复核）：

| 组 | 候选项 | 适用说明 | 代码位置 |
|---|---|---|---|
| A. Attention 后端 | `torch`、`xformers`、`sageattn`、`flash`（= `flash2`） | `sdpa` 是 `torch` 的别名，`flash` 和 `flash2` 走同一分支，**不重复测**。`flash3` 仅支持 Hopper，**本机硬件不适用** | `wan/modules/attention.py` |
| B. 精度与量化 | 无 / `--fp8` / `--fp8_scaled` / `--fp8_scaled --fp8_fast`；T5 侧 `--fp8_t5` | `--fp8_fast` 只在 `--fp8_scaled` 分支内生效；文档称其"似乎会降低输出质量" | `modules/fp8_optimization_utils.py` |
| C. 显存卸载（原 16G 目标暂缓） | `--blocks_to_swap` 档位；`--vae_cache_cpu`；与 B 组组合 | 服务器按瓶颈需要选择；为本机筛配置暂缓 | `modules/custom_offloading_utils.py` |
| D. 采样与调度 | `--infer_steps`；`--flow_shift`；`--guidance_scale`；`--cfg_skip_mode` + `--cfg_apply_ratio` | 改变的是计算量而非实现，**质量代价必须同报** | `modules/scheduling_flow_match_discrete.py` |
| E. 编译 | `--compile` | 报稳态加速比与首次编译开销 | `utils/model_utils.py`（`compile_transformer`） |
| F. VAE 解码 | **时间维已逐帧解码**（`WanVAE_.decode` 逐个 latent 帧 + 特征缓存，`torch.cat` 拼接输出）；**无空间分块**；输出在 GPU 上逐帧累积 | 若阶段 1 显示 VAE 解码是峰值来源，先定位峰值来自哪种分配（单帧全分辨率激活、特征缓存还是输出累积），再针对它改。**不重复实现时间分块** | `wan/modules/vae.py` |

**已删除的项**（V2.0 中误列）：

- `sdpa`：与 `torch` 是同一路径。
- `flash3`：需要 H100/H800。
- `--offload_inactive_dit`、`--lazy_loading`：源码中只在设置 `--dit_high_noise`（即 Wan2.2 双 DiT）时生效，对 1.3B 单 DiT 不起作用。

**组 C 的目标**：48G 卡跑 1.3B 预计不缺显存，在这张卡上卸载只会更慢。因此组 C 的问题定为：

> **在本机 RTX 5060 Ti 16G 上能否让 1.3B 480P 跑起来？哪些配置可以运行，各自的延迟与质量如何？**

**两台机器的结果分两张表，分别解释**：

- **服务器表**：配置之间的显存—延迟权衡，只用于**筛选**本机候选；
- **本机表**：实际跑通的配置，以及它们的耗时与质量。

服务器上的曲线**不能直接推出**本机的配置排名。本机只验证了一个配置时，结论只能写"找到可运行配置"。只有比较过多个可运行配置，才能写"在已测配置中代价最小"。

**本机执行顺序**：先确定能跑通的 attention 后端（预编译包可能缺失，从 `torch` 开始），**固定这个后端**之后，再逐步加 fp8 / `--blocks_to_swap` / `--vae_cache_cpu` 压显存。

**交付**：
- 瓶颈驱动的对照表：每行包括配置、延迟、峰值显存、质量判据、机理一句话、失效条件；
- 本人代码改动及其前后对照；
- 16G 可用性结论暂缓，不是当前阶段交付门槛；仅报告服务器实测权衡。

**止损线**：每个候选项预算上限 2 天。超时就记录"已尝试，未打通/收益不明确"，然后继续往下。

### 阶段 3：训练闭环与 LoRA

**目标**：跑通训练 → 保存 → 重新加载 → 验证的完整链路，训出一个可用的单人物动作 LoRA。

- 最小闭环：数据缓存 → 短程 LoRA 训练 → 保存权重 → 重新加载 → 验证生成。
- 代码学习重点：
  - 数据和 caption 怎样进入训练；
  - LoRA 的注入位置（`networks/lora_wan.py`）；
  - 时间步采样和损失在哪里实现；
  - 训练产物怎样加载到推理。
- 训练侧显存调优：`--blocks_to_swap` 档位、fp8、梯度检查点。
- 数据按第六节的规则筛选和划分。

**交付**：可重复运行的最小闭环 + 资源记录 + 一个 LoRA 权重 + 首帧/末帧对照视频。

**止损线**：两周内找不到可用的数据来源，就先用自采或小规模数据跑通闭环，数据问题单独处理。

### 阶段 4：两线收口

**4a. 主线收口**：把阶段 2 的结论整理成权衡表，并写明各自的适用条件。

**4b. 次要线（时间步与 LoRA 配置）**：在阶段 3 的闭环上跑少量训练配置，观察动作和外观上的差异。

- 变量：`--timestep_sampling`、`--discrete_flow_shift`、`--min_timestep/--max_timestep`、`--preserve_distribution_shape`。
- 上游文档写明这些值"需要通过实验确定"。这说明待测问题真实存在，但不保证会有正效应。
- 初筛只用单训练种子，**结论只作探索性**。样本量小，结论强度天然较低，**不追加预算**。

**交付**：权衡表 + 次要线的探索性观察（有正效应写正效应，null 也照写）。

**止损线**：次要线 3 周内没有明确效应，就写成一页探索记录收尾，不再投入。

### 阶段 5：Demo 与发布

- Gradio / HF Spaces demo：选择或输入提示词 → 生成 → 展示延迟与显存。
- 仓库整理：README、复现步骤、依赖与许可清单，以及"上游版本 vs 本人修改"的 diff 说明。
- 上游 PR：见第八节。
- 发布合规：训练素材、适配器权重、新增依赖分别核对许可。许可不明确的产物不发布，并说明限制。

**交付**：可点开的 demo + 可复现仓库 + 实验报告 + 合规说明。

## 四、变量纪律

- **一次只动一个变量**。测 attention 后端时其他全部固定；测步数时后端固定。
- **训练侧与推理侧分开归因**。第一轮只改推理侧配置，训练侧实验单独开展。
- 训练 shift 和推理 shift 分字段记录，不要用一个含混的 "shift" 字段代替。
- 数据、训练预算、LoRA 配置尽量保持一致，具体值在正式对照前确定。
- **生成种子估计出片随机性，训练种子检查训练稳定性，两者不能互相替代。**

## 五、双卡分工

**纪律**：先保证单卡闭环跑通。不把两张 48G 卡当作一张透明的 96G 卡。双卡跑的是独立任务，不需要 DDP。

| 资源 | 用途 |
|---|---|
| 卡 0 | 主线：推理测量与优化、训练闭环 |
| 卡 1 | 条件允许时跑无状态耦合的并行任务：另一组候选项、基线生成、计时重复 |
| 本机 5060 Ti 16G | **组 C 的实机验证平台**（延后执行，计划保留，建议第 8 周里程碑前完成）；代码阅读、小规模冒烟测试、指标计算 |

**卡 1 不能替代什么**：改生成种子只能估计出片随机性，**不能**说明不同训练种子下的 LoRA 是否稳定。

**预期用法（未验证，见 A4.2）**：用第二张卡增加重复次数，换取更可信的数字，而不是跑更多配置。

## 六、数据筛选与划分（阶段 3 前置）

**先定训练目标，再定数据源。**

**检查内容**：

- 许可是否支持拟开展的用途。训练、素材再分发、权重发布要**分别判断**。
- 动作标签是否可信，人体是否完整，有无严重遮挡、模糊或镜头不匹配。
- 帧数、尺寸、帧率/时间戳和连续性，能否支撑训练片段的组织（帧数约束为 4n+1）。
- 是否有可复核的原始序列或来源分组。

**划分规则**：按原始来源分组，划分训练/开发/独立测试三部分。同一来源的相关片段不能同时出现在训练集和独立测试集里。

**不做**：不先全量下载；不开发复杂的筛选器；**不用丢帧或插帧硬凑出数据可用性**。

## 七、已知冲突与依赖（已对照源码，2026-10-11 main）

| 项 | 源码中的实际行为 | 备注 |
|---|---|---|
| `sdpa` | 与 `torch` 是**同一路径**（`wan/modules/attention.py` 同一分支） | 只测 `torch` |
| `flash` / `flash2` | 同一分支，调用 `flash_attn.flash_attn_func` | 只测一个 |
| `flash3` | 需要 `flash_attn_interface`；FlashAttention-3 仅支持 Hopper | 本机硬件不适用 |
| `--offload_inactive_dit` | 只在设置了 `--dit_high_noise` 时生效（Wan2.2 双 DiT）。与 `--lazy_loading` 有 assert 互斥 | 1.3B 不适用。**V2.0 写成"与 blocks_to_swap 互斥"是错的**：那是文档说法，推理代码中二者可以共存 |
| `--lazy_loading` | 只在多 DiT 时生效 | 1.3B 不适用 |
| `--fp8_fast` | 2026-10-14 固定 checkout 副本复核：入口传入 `use_scaled_mm`，真正安装 FP8 线性层补丁受 `fp8_scaled` 分支控制；没有显式依赖校验 | 务必和 `--fp8_scaled` 一起开，否则单独开启不会激活该优化路径 |
| `--blocks_to_swap` | 2026-10-14 固定 checkout 副本复核：1.3B 为 30 层，模型内部 assert 检查 `blocks_to_swap <= num_blocks - 1`，最多 29 | **纠正此前“代码不校验上限”**；见 `../notes/param_check.md`，尚未做卸载性能实测 |
| `--device` | **存在**，默认 cuda/cpu 自动选择 | V2.0 误写为不存在 |
| VAE 解码 | 时间维已逐帧解码 + 特征缓存；无空间分块；输出在 GPU 上 `torch.cat` 累积；`cache_device` 只决定缓存特征放在哪里（输出卸载分支在源码中被注释掉） | 空间分块或输出累积方式是候选；**V2.1 写成"一次解码全部"是错的**（依据仅为调用处，未读内部实现） |
| 阶段计时 | 上游无计时 | 需自行插桩 |
| `--compile` 与动态 shape | 换分辨率或帧数会触发重编译 | 测量时固定 shape |
| attention 后端可用性 | xformers / sageattention / flash-attn 需单独安装；5060 Ti 是新架构，预编译包可能缺失 | 安装失败也要记录 |
| 显存与速度非单调 | 量化、卸载都可能变慢 | **不以显存下降推导速度提升** |

## 八、上游 PR（贯穿全程）

零论文的情况下，**一个具体、经过验证的上游贡献很有说服力**。是否被合并由维护者决定，所以本项目的交付标准是**提交**，合并结果如实记录。

- 候选方向：阶段计时/性能日志、VAE 空间分块或输出累积优化（视测量结果而定）、文档与代码不一致处的修正（如第七节的 `--offload_inactive_dit` 说明）、`--fp8_fast` 未配 `--fp8_scaled` 时给出警告。
- 纪律：PR 小而明确，一个 PR 只做一件事；遵守上游代码风格；先开 issue 讨论，再动手，避免大改动被拒。
- 记录：PR 链接和状态写入 README 交付清单。

## 九、表述纪律

- 上游已有的能力，不写成本人从零实现。本人的工作围绕**测量、定位、修改、对照、解释**展开。
- "提升"只能由独立测试支持，不能由训练 loss 或"更像训练集"推出。
- 未检出差异就写未检出，并限定在当前任务、配置与评价口径之内。
- 不夸大：本项目做的是**瓶颈分析与工程优化**，不是提出新的推理加速算法。
- 硬件规模本身不算简历成果。

削减优先级：**先削候选项个数，不削减验证提示词集。**
