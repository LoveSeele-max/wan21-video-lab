## 5. 网络与断开 SSH 的问题

最初 GitHub 直连超时。我们通过 `ss -lntp` 找到服务器代理监听端口 `127.0.0.1:7897`，再通过 curl 检查能否访问 GitHub。

`127.0.0.1` 指命令所在机器自身：服务器上的这个地址不是本机 Windows 的代理地址。

```bash
# 单次 Git 命令使用代理，不修改全局 Git 配置
git -c http.proxy=http://127.0.0.1:7897 clone https://github.com/kohya-ss/musubi-tuner.git
```

curl 中 `200 Connection established` 只说明代理隧道建立；后续 GitHub 的 `HTTP/2 200` 才支持访问成功。

生成日志还显示访问 HF 镜像，之后确认当前终端 `HF_ENDPOINT=https://hf-mirror.com`。我们据此修正了之前“没用镜像”的记录，说明**原始日志可能揭示命令表面没有写出的环境条件**。

### tmux

普通 SSH 终端中的长任务不能直接假定断线后继续运行。我们使用 tmux 会话来保护长时间下载。

```bash
# 服务器操作速查；不要盲目重复创建已有会话
tmux new -s wan21
# 在这个会话内激活环境、启动长任务
# 脱离画面：先按 Ctrl+B，松开，再按 D
# 以后回来：
tmux attach -t wan21
```

只创建一个 tmux 会话，不会把已经在普通终端启动的任务自动移进去。服务器仍需保持运行。

## 6. 三个模型组件分别负责什么

| 组件 | 初学阶段的理解 | 我们下载的文件 |
|---|---|---|
| T5 | 将提示词转换为模型能使用的数值表示 | `models_t5_umt5-xxl-enc-bf16.pth`，约 11G |
| DiT | 根据文本条件逐步更新初始噪声，生成 latent | `wan2.1_t2v_1.3B_bf16.safetensors`，约 2.7G |
| VAE | 将 latent 解码为视频画面 | `wan_2.1_vae.safetensors`，约 243M |

latent 是模型内部的压缩表示，不能直接当成 MP4 播放。本次同时保存视频和 latent，后者也可留给后续解码研究。

权重文件计算了 SHA256。它像文件内容的指纹，可用于比较是否变化。**只算出指纹并不等于已经与下载来源校验值比较过。**

## 7. 第一条视频实际怎样生成

阅读源码后，本次普通 T2V、单提示词的顺序是：

```text
读取命令参数，补上未指定的默认值
  → 加载 T5，编码正面和负面提示词
  → 删除 T5 对象并清理内存
  → 创建初始噪声，加载 DiT
  → 建立采样器，执行 20 步采样
  → 删除 DiT 对象并清理内存
  → 保存 latent
  → 加载 VAE，将 latent 解码
  → 保存 MP4
```

三个组件不是始终一起驻留。源码中的清理操作不代替实际显存测量。

### 本次参数

| 参数 | 实际值 | 含义 |
|---|---|---|
| task | t2v-1.3B | 文本生成视频，1.3B 模型 |
| video_size | 480 832 | 参数顺序为高、宽；视频宽 832、高 480 |
| video_length | 81 | 输出帧数，符合 4n+1 |
| fps | 16 | 播放帧率，视频约 5 秒 |
| infer_steps | 20 | 采样的迭代步数，不是视频帧数 |
| seed | 42 | 本次生成使用的随机种子 |
| attn_mode | torch | 选择 attention 实现路径 |
| sample_solver | unipc | 没有显式指定，由参数默认值补齐 |
| flow_shift | 5.0 | 从任务配置补齐，用于采样时间步安排 |
| guidance_scale | 5.0 | 从任务配置补齐，用于组合条件/负面条件预测 |
| output_type | both | 保存视频与 latent |

提示词原文：

```text
A person waving one hand, plain background, static camera.
```

任务默认步数是 50，但命令显式传入了 20，程序只给未设置的参数补默认值，因此实际仍为 20。命令参数读入后保存在 `args` 对象中，例如 `args.infer_steps = 20`。

负面提示词没有显式输入，但程序用了共享配置中的默认文本，里面包括多余手指、画得不好的手部、手指融合等描述。它表达生成时希望避免的内容，不构成保证输出正确的硬约束。

`--save_path` 是输出目录，不是我们指定的 MP4 文件名。

### 两张卡怎样切换

第一条使用 `CUDA_VISIBLE_DEVICES=0`，第二条使用 `CUDA_VISIBLE_DEVICES=1`，保持生成设置一致，分开输出与日志目录。

这个变量决定该进程能看到哪些 GPU。只暴露物理 GPU 1 时，程序内部可能仍称它为 `cuda:0`，不能据内部编号断言用了服务器物理卡 0。

## 8. 实际结果与能得出的结论

| 指标 | GPU 0，第一次 | GPU 1，第二次 |
|---|---|---|
| 退出状态 | 0 | 0 |
| 含加载、生成、保存的总耗时 | 157.61 秒 | 139.70 秒 |
| 进度条报告的去噪耗时 | 约 108 秒 | 约 107 秒 |
| MP4 | 832×480、81 帧、16 FPS | 相同 |
| latent 文件 | 已确认存在，显示 8.0M | 已确认存在，显示 8.0M |
| GPU 峰值显存 | 未测 | 未测 |

两份本机 MP4 都为 2526841 字节，文件 SHA256 相同。全部 81 帧解码为 RGB 后也一致。latent 只检查存在和大小，没有重新加载或比较内容。

这支持“本次相同参数、相同种子的两次输出一致”，不支持所有硬件、依赖和种子下都必然一致。seed 是复现条件之一，不是跨所有环境完全一致的保证。

第二次总时间少 17.91 秒，但去噪时间接近，而且 tokenizer 请求和缓存状态不同。各跑一次，不能认定 GPU 1 更快，也不能准确拆出差异原因。

`time -v` 的 Maximum resident set size 是 **CPU 内存峰值**，不是 GPU 显存峰值。user time、system time 是 CPU 时间，不应当作视频生成的墙钟延迟。去噪进度条也不等于同步、分阶段的正式测量。

### 视频质量

用户连续播放观察到：手在挥动，但手腕、手掌和手指的运动关系不符合人体规律。

记录为**动作发生，但存在动作与时序结构缺陷**。抽帧能辅助检查形态，不能替代连续动作评价。

本次没有证据证明问题是安装错误、第一次运行、20 步不足或某个配置单独导致。即使 50 步是默认值，也不能直接声称换到 50 步就会解决。失败样本已保留。

## 9. 源码核对真正帮我们避开了什么

| 核对结果 | 为什么有用 | 还不能声称什么 |
|---|---|---|
| torch/sdpa 是同分支，flash/flash2 是同分支 | 避免把别名当成不同后端重复实验 | flash 已安装、比 torch 快 |
| DiT 有 30 个 block，卸载 assert 上限为 29 | 避免只查生成入口后误认代码没有上限校验 | 卸载 29 个已实测可用或更快 |
| fp8_fast 的线性层补丁依赖 scaled FP8 路径 | 避免只开 fast 却没有启用有效优化路径 | FP8 已有性能收益 |
| inactive DiT/lazy loading 针对双 DiT 路径 | 避免在本次单 DiT 上做无效开关实验 | 两个开关可以同时使用 |
| VAE decoder 已逐 latent 时间片解码并使用缓存 | 避免重新实现已有的时间分块 | VAE 所有操作都完全流式 |
| vae_cache_cpu 移动特征缓存，输出卸载分支被注释 | 避免把缓存卸载误当成整个输出卸载 | 显存减少了多少 |
| 编译工具按 block 调用 torch.compile | 定位后续编译实验的代码入口 | 编译必然加速 |

VAE 中 `conv2(z)` 仍先处理整个 latent，然后 decoder 逐时间片运行并用 `torch.cat` 累积输出。这些只是后续测量候选点，目前没有测出它是显存瓶颈。

12 项核对依据服务器传回的源码副本和文件清单，已记录位置与行号；副本没有另逐文件与 Git 对象校验。具体证据见 [参数核对](../param_check.md)。

## 10. 本周最值得记住的错误

| 当时的问题或误解 | 正确处理 |
|---|---|
| 进入 env 文件夹就算激活了环境 | 查看实际 Python/pip 路径，正确激活 |
| 在 base 找不到 torch，认为安装失败 | 先检查当前环境 |
| 浏览器能联网，终端也必然能联网 | 单独检查终端代理和实际响应 |
| 一看到 SageAttention 导入失败就补装 | 本次 torch 路径已能运行，保留可选依赖状态 |
| 以为尺寸顺序是宽、高 | 以帮助、源码和实际输出确认高、宽 |
| 把 save_path 当作 MP4 文件名 | 使用目录，程序自动命名 |
| 手在动就算动作生成成功 | 连续检查运动规律与指令符合度 |
| 总时间短就认定显卡更快 | 保持公平条件、重复测量、拆开阶段 |
| 文件有哈希就算来源已验证 | 哈希记录与来源校验是两项工作 |
| 安装依赖就是项目核心成果 | 它是基础；后续测量、改动和对照才形成主要工程产出 |

2. cd 改目录，activate 切换当前终端使用的 Python 环境。
